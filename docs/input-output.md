# Input and output

`.input()` declares what a route reads, each source validated by a Standard Schema (zod, valibot, arktype):
`search`, `headers`, `cookies`, and one body, `json`, `form` or `binary`, plus the path params that need more than a
string. A request that fails validation is answered 400 with the failing fields, and `ctx.input` holds the parsed
values, typed. Path params are strings by default and need no schema; `params` takes a schema per param, by name
(`{ params: { provider: z.enum(["github", "google"]) } }`), validated onto `ctx.params` beside the undeclared ones.
A name the path does not have is a type error and throws at registration.

`.output()` declares what it answers, the media type as the outer key and the status as the inner one. A media type
takes the 2xx statuses as its inner keys, `redirect` takes the 3xx ones (the redirects and `not_modified`), and
`headers` takes any 2xx or 3xx status with a schema of the headers it carries, which reach the OpenAPI document and the
SDKs' typed accessors. An error answer is declared with `.errors()`, never in `.output()`. Any media type works,
`image/gif` or `application/zip` included. Inside `.output({ })` an editor completes the seven media types honey has a
helper for (`application/json`, `application/octet-stream`, `application/xml`, `text/csv`, `text/event-stream`,
`text/html`, `text/plain`), the 2xx keys, `headers` and `redirect`; inside a media type it completes the 2xx keys, and
inside `redirect` the 3xx ones. A custom `type/subtype` compiles with no completion, and so does a misspelled one such
as `text/cs`.

A 204 is declared as `no_content: true`, in the shorthand or under a media type, and is documented with no body. On a
route with `.output()`, `ctx.res.noContent()` exists only then; a route without `.output()` keeps it. The body helpers
take no `no_content` or `reset_content` key, since neither status carries a body.

A key the route cannot answer is a type error, and its message names the key and where it goes:

```text
not_found is an error status: declare it with .errors(), not .output()
found is a redirect: declare it under redirect
not_found is no 3xx status
ok beside a media type: write JSON as "application/json": { ok: ... }
okay is no status key
```

The first is a 4xx or 5xx key in a body slot or under `headers`, the second a 3xx key in a body slot, the third a key
under `redirect` that is no 3xx, the fourth a status key beside a media type, and the last a key that names no status.
Untyped, each one fails where the app is documented (`honey generate`, `generateOpenApi`, `serveOpenApi`), naming the
route and the key, as in `GET /x: .output() key "not_found" under application/json is no 2xx status; an error answer
is declared with .errors()`; serving requests never checks it.

`ctx.res` builds the answer: `json`, `text`, `html`, `binary`, `sse`, `redirect`, and `raw` for any `Response`. A
status is always a key, never a number: `ctx.res.json("created", body)`, and `ctx.res.redirect("found", url)` at a 3xx
key. Under `.output()` the handler may return only a declared media type at one of its status keys, a declared 204,
or a redirect at a key the `redirect` entry declares (`ctx.res.redirect` is gone without one), so `raw` is gone there;
`text`, `html`, `csv`, `xml`, `binary`, `json` and `sse` also take a `ReadableStream` body, sent as it comes and never
validated. honey checks each answer against the declaration: its media type, its declared headers, and a JSON body
that is no stream against its status's schema. A production `vite build` through `honeyPlugin()` drops that check,
unless `honeyPlugin({ outputValidation: true })` keeps it; see [the plugin page](plugin.md#output-validation).

Where the status is decided elsewhere (a stored file's 206 or 304, an upstream service's answer),
`ctx.res.forward(response)` answers that `Response` as it is, and never reads its body. A status `.output()` declares
passes when its media type, without parameters, is declared at that key, or when it has no body. A status one of the
route's error keys answers with passes as the upstream gave it, whatever its media type. Those keys are the route's
`.errors()`, its middleware's and the app's `defaultErrors`; a route that declares none takes every key of the app's
factory. Any other answer is refused as an undeclared answer is, a 500 `output_validation_failed` or
`output_content_type_mismatch`, whatever the build. A bodiless status such as that 304 is declared under `redirect`,
which documents it with no body, and with a `Location` only at the 3xx keys `redirect()` answers.

Status keys alone declare JSON: `.output({ ok: schema })` is `.output({ "application/json": { ok: schema } })`, with
`headers` and `redirect` beside them as in the full form; the two forms do not mix. When a route declares one 2xx
status under one media type, other than an event stream, and that status declares no headers, the handler may return
the body itself, and honey answers it at that status through the type's helper. With two success statuses or two
media types, build the answer with `ctx.res`.

## Example

```ts
import { defineErrors, honey } from "@workerstack/backend"
import * as z from "zod"

const errors = defineErrors({})

const app = honey()

app
	.get("/books/:id")
	.input({ search: z.object({ lang: z.string().optional() }) })
	.output({ ok: z.object({ id: z.string(), title: z.string() }) })
	.errors(errors, "not_found")
	.handler((ctx) => {
		if (ctx.params.id === "0") throw errors.not_found()
		return { id: ctx.params.id, title: "Dune" }
	})

app
	.post("/books")
	.input({ json: z.object({ title: z.string().min(1) }) })
	.handler((ctx) => ctx.res.json("created", { id: "b-1", title: ctx.input.json.title }))
```
